## 1. 引言

### 1.1 编写目的

本文档面向统一应用软件权限管理系统（以下简称 "本系统" 或 "权限平台"）的需求分析阶段，系统性地定义本系统的业务背景、用户角色、功能需求、非功能需求、对外接口与验收要点，作为后续概要设计、详细设计、编码实现与测试验收的依据。

本文档的预期读者包括：



* 甲方业务代表（信息中心、人力资源部、各分公司综合办公室）；

* 系统分析师、架构师、开发与测试人员；

* 课程指导教师与评审人员；

* 后续承接运维的技术人员。

### 1.2 项目范围

#### 1.2.1 本系统做什么（In Scope）



1. **统一身份管理**：对接入企业全体员工建立统一账号，覆盖多级树状组织机构（总公司、分公司、部门、项目部等）的组织归属。

2. **统一认证（SSO）**：为各接入业务系统提供单点登录与统一身份认证。

3. **统一授权**：以 RBAC 模型（课程范围 RBAC0 为基础，辅以数据权限维度）统一管理功能权限与数据权限，向各接入系统提供令牌与接口鉴权能力。

4. **双维度权限控制**：功能权限（系统→模块→功能点→操作）与数据权限（分公司 / 部门 / 项目 / 本人范围）并行管理。

5. **权限全生命周期管理**：人工手动授予与调整、调岗变更、离职封存、权限回收。

6. **前端控制与后端控制双重校验**：前端按权限控制菜单 / 按钮 / 页面元素的可见与可用；后端对每个 API 调用做服务端权限校验。

7. **权限即时生效**：后端权限变更后，前端无需重新登录、无需手动刷新即生效（缓存失效 / 推送更新）。

8. **操作审计日志**：日志永久保存，字段至少包含操作时间、操作内容 / 动作、用户名、操作成功与否，支持查询与导出。

9. **敏感信息保护**：员工姓名、电话号码等敏感个人信息加密存储、展示脱敏。

#### 1.2.2 本系统不做什么（Out of Scope）



1. **不重写任何业务系统**：各接入业务系统的业务功能、业务流程、业务数据仍由原系统负责，本系统只做统一身份与鉴权，不替代其业务处理。

2. **不新建业务功能点**：功能点以各接入系统现有功能点及其权限取值集合为管理对象，不重新定义业务操作语义。

3. **不做物理删除**：员工离职采用 "封存（禁用）" 而非删除账号，日志不做定期删除。

4. **不承担人事主数据维护职责**：员工入职、调岗、离职的人事事实由人力资源管理系统产生，本系统接收并执行权限侧处理（人工手动授予 / 调整仍为本系统职责）。

5. **不提供统一门户页面聚合**：本系统提供认证与鉴权能力，不负责各接入系统的界面整合与内容聚合。

### 1.3 术语定义



| 术语        | 定义                                                                                                                                           |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| RBAC      | 基于角色的访问控制（Role-Based Access Control）。本系统以 RBAC0 为基础：用户 — 角色 — 权限三层绑定，用户通过角色获得权限。                                                             |
| 功能权限      | 对 "能进哪套软件、哪个菜单、哪个按钮 / API、可执行何种操作" 的控制，操作取值包括：无、查看、全部、查看 / 编辑、查看 / 新增、查看 / 审批、查看 / 导出、查看 / 编辑 / 审批、查看 / 新增 / 编辑、查看 / 编辑 / 导出、查看本人、查看 / 编辑本人。 |
| 数据权限      | 对 "能看 / 能操作哪个分公司、部门、项目的数据" 的控制，范围包括：全公司、本分公司、本部门、本项目、本人。"本人" 表示仅能操作本人 / 本项目的数据，是数据权限雏形。                                                      |
| SSO       | 单点登录（Single Sign-On）。用户一次认证后可访问其有权限的各接入业务系统，无需重复登录。                                                                                        |
| 令牌（Token） | 本系统签发的、用于业务系统识别用户身份与权限的凭证，业务系统凭令牌向本系统校验身份与权限。                                                                                                |
| 封存        | 员工离职后保留账号但禁用（不可登录、不可被授权），解绑其业务角色与数据权限，不做物理删除；其历史日志保留可查。                                                                                      |
| 脱敏        | 对敏感个人信息（姓名、电话号码等）在展示时按规则遮蔽（如姓名保留姓氏、电话中间四位掩码），存储时加密。                                                                                          |
| 功能点       | 业务系统中可被授权的最小功能单元（菜单 / 按钮 / API 对应的操作集合）。                                                                                          |
| 互斥        | 两个角色或两项授权在同一用户 / 同一资源上不能同时生效的约束；并发冲突操作需加锁互斥处理。                                                                                               |
| 即时生效      | 后端权限变更后，前端在无需重新登录、无需手动刷新的情况下获得最新权限（缓存立即失效或推送更新）。                                                                                             |
| 最小权限      | 只授予完成工作所必需的最小功能权限与最小数据范围。                                                                                                                    |

## 2. 项目背景与业务现状

本系统为**通用统一权限管理平台**，面向存在多业务子系统、需集中管控身份与权限的各类企业组织。以下以首个接入案例（某市政公司）为参照，说明典型业务背景与规模量级。

### 2.1 首个接入案例的组织规模（参考）



* **员工总数**：10000 人。

* **单位构成**：1 个总公司（约 190 人）+ 9 个分公司（各约 1090 人），分公司为：道路工程分公司、桥梁工程分公司、隧道工程分公司（承担海底隧道业务）、轨道交通分公司、管网工程分公司、水务工程分公司、园林绿化分公司、照明工程分公司、市政养护分公司。

* **部门总数**：111 个，呈多级树状：


  * 总公司职能部门：综合办公室、党委工作部、人力资源部、财务部、市场经营部、工程技术部、安全质量部、物资设备部、审计监察部、工会办公室等；

  * 各分公司下设职能部：综合办公室、财务部、工程技术部、安全质量部、物资设备部、市场经营部；

  * 各分公司下设项目经理部：第一～第四项目经理部。

* **与权限强相关的典型岗位**：公司领导（董事长 / 总经理 / 副总经理 / 总工程师 / 总会计师等）、部门经理（部长 / 主任）、项目经理、安全员（约 871 人）、预算员（约 820 人）、质检员（约 751 人）、造价员、施工员、技术员、材料员、资料员、会计、出纳等。

* **现有功能矩阵粗分 5 类角色**：系统管理员、公司领导、部门经理、项目经理、普通员工。

### 2.2 在跑业务软件现状

公司现有 18 套在跑业务系统，本系统不重写业务，而是统一为它们做鉴权：



1. OA 协同办公系统；2. 企业即时通讯系统；3. 企业知识库管理系统；4. 人力资源管理系统；5. 财务管理系统；6. 工程项目管理系统（PMIS）；7. 招投标管理系统；8. 物资设备管理系统；9. 移动巡检 APP；10. 工地 AI 视频监控系统；11. GIS 地下管线管理系统；12. 企业档案管理系统；13. 车辆管理系统；14. 企业宣传平台；15. 安全生产管理系统；16. 合同全生命周期管理系统；17. 成本管控系统；18. 系统管理后台。

* 功能点总数约 **359 个**。

* 现有功能点权限取值集合：无、查看、全部、查看 / 编辑、查看 / 新增、查看 / 审批、查看 / 导出、查看 / 编辑 / 审批、查看 / 新增 / 编辑、查看 / 编辑 / 导出、查看本人、查看 / 编辑本人。

### 2.3 当前痛点



1. **"一人一系统一套权限"**：每套系统各自维护账号与权限，同一员工在 18 套系统中有 18 份账号与权限记录，入职、调岗、离职需逐系统手工处理，易漏改、易残留。

2. **权限口径不一致**：同一岗位在不同系统中权限范围不同，缺乏统一角色与数据范围定义，越权与权限不足并存。

3. **离职账号清理不及时**：离职员工账号可能仍可登录部分系统，存在安全风险；且缺乏统一封存与日志追溯手段。

4. **前端隐藏代替后端校验**：部分系统仅靠前端隐藏菜单 / 按钮，直接调用 API 可越权。

5. **权限变更生效慢**：权限调整后需重新登录或等待缓存过期，影响业务与安全响应。

6. **敏感信息保护不足**：员工姓名、电话号码等明文存储与展示，存在泄露风险。

7. **日志留存不合规**：部分系统日志定期删除，无法满足永久保存与审计追溯要求。

本系统的建设目标即针对上述痛点，建立公司级 IAM（身份与访问管理）平台，实现统一认证、统一授权、双维度权限控制、即时生效与永久审计。

## 4. 功能性需求

优先级说明：**高**＝必须实现，缺失则系统不可验收；**中**＝应实现，影响体验与完整性；**低**＝可延后实现。

### 4.1 用户与账号管理



* **FR-01（高）** 系统应支持员工统一账号的建立，账号唯一标识员工，关联姓名、电话（加密存储）、所属组织（总公司 / 分公司 / 部门 / 项目经理部）、岗位。

* **FR-02（高）** 系统应支持账号状态管理：正常、停用、封存（离职）、锁定（异常），状态变更需记录操作日志。

* **FR-03（高）** 员工入职时，系统应支持由系统管理员人工创建账号并授予初始角色；支持从人力资源管理系统接收人员事件作为触发（人事事实以 HR 系统为准）。

* **FR-04（高）** 员工调岗时，系统应支持调整其组织归属与岗位，并触发权限复核与变更流程（见 5.2）。

* **FR-05（高）** 员工离职时，系统应执行封存：保留账号、禁用登录、解绑全部业务角色与数据权限、日志保留，不做物理删除（见 5.3）。

* **FR-06（中）** 系统应支持账号批量导入与批量状态变更，操作需二次确认并记录日志。

* **FR-07（中）** 系统应支持账号与角色的绑定关系查询，展示某用户当前全部功能权限与数据权限。

### 4.2 组织机构管理



* **FR-08（高）** 系统应支持多级树状组织管理：总公司→分公司（9 个）→部门（111 个，含总公司职能部门、分公司职能部）→项目经理部（第一～第四项目经理部）。

* **FR-09（高）** 组织节点应支持新增、修改、停用、移动（调整上级），移动需校验不影响历史日志归属（日志保留原组织快照）。

* **FR-10（中）** 系统应支持组织节点与数据权限范围的映射，作为数据权限 "本分公司 / 本部门 / 本项目" 范围的判定依据。

* **FR-11（中）** 系统应支持组织树查询与导出，展示各节点人数统计。

### 4.3 角色管理



* **FR-12（高）** 系统应支持角色定义：角色编码、名称、类型（功能角色 / 岗位型数据角色）、描述、状态。

* **FR-13（高）** 系统应支持角色继承：子角色继承父角色的功能权限与数据权限，可叠加扩展；继承关系需可视化展示，禁止循环继承。

* **FR-14（高）** 系统应支持角色互斥：互斥角色不能同时授予同一用户（如会计与出纳操作互斥），授予时校验并拒绝冲突。

* **FR-15（中）** 系统应支持角色复制、角色停用；停用角色不影响已产生的历史日志。

* **FR-16（中）** 系统应预置 5 类基础功能角色（系统管理员、公司领导、部门经理、项目经理、普通员工）及岗位型数据角色模板（安全员、预算员、质检员、造价员、会计、出纳等）。

### 4.4 功能权限管理



* **FR-17（高）** 系统应支持以 "软件系统→模块→功能点→操作" 四级结构管理功能权限，覆盖 18 套系统、约 359 个功能点。

* **FR-18（高）** 功能点操作取值应支持现有集合：无、查看、全部、查看 / 编辑、查看 / 新增、查看 / 审批、查看 / 导出、查看 / 编辑 / 审批、查看 / 新增 / 编辑、查看 / 编辑 / 导出、查看本人、查看 / 编辑本人。

* **FR-19（高）** 系统应支持功能点与后端 API 的映射登记（API 路径 + 方法），作为后端鉴权依据。

* **FR-20（中）** 系统应支持功能权限的批量授予与批量回收，操作记录日志。

* **FR-21（中）** 系统应支持按系统 / 模块 / 角色 / 用户多维度查询功能权限矩阵并导出。

### 4.5 数据权限管理



* **FR-22（高）** 系统应支持数据权限范围授权：全公司、本分公司、本部门、本项目、本人。

* **FR-23（高）** 系统应支持岗位型数据角色的差异化数据范围配置：安全员、预算员、质检员、造价员、会计、出纳等按岗位设定默认数据范围（见第 8 章汇总表）。

* **FR-24（高）** 数据权限应与功能权限联合判定：用户对某功能点有操作权限，且对目标数据在授权范围内，方可执行。

* **FR-25（中）** 系统应支持数据权限的临时授权（带有效期），到期自动回收并记录日志。

* **FR-26（中）** 系统应支持 "本人 / 本项目" 数据范围的判定规则配置（以用户 ID、项目 ID 为过滤条件）。

### 4.6 授权与回收



* **FR-27（高）** 系统应支持人工手动授予 / 调整权限：角色 — 功能点授权、角色 — 数据范围授权、用户 — 角色绑定，全部操作留痕。

* **FR-28（高）** 系统应支持权限回收：解除用户 — 角色绑定、回收角色 — 功能点 / 数据范围授权，回收即时生效。

* **FR-29（高）** 系统应支持权限继承：用户通过角色继承获得权限，继承链上的权限变更对用户即时生效。

* **FR-30（中）** 系统应支持授权申请 — 审批 — 执行流程（部门经理 / 项目经理审批，系统管理员执行），审批记录纳入审计日志。

### 4.7 统一认证与对外鉴权



* **FR-31（高）** 系统应提供 SSO 单点登录：用户一次认证后可访问其有权限的 18 套业务系统，无需重复登录。

* **FR-32（高）** 系统应签发令牌（Token），令牌应包含用户标识、有效期、签名，支持校验与吊销。

* **FR-33（高）** 系统应向 18 套业务系统提供鉴权接口：校验令牌有效性，返回该用户在该系统的功能权限与数据权限。

* **FR-34（高）** 系统应支持令牌过期与续期策略，令牌吊销后业务系统鉴权应立即失败。

* **FR-35（中）** 系统应支持业务系统接入登记（系统编码、回调地址、密钥），作为第 19 套系统接入的扩展点。

### 4.8 前端可见 / 可用控制与后端 API 鉴权双重控制



* **FR-36（高）** 前端应依据权限控制菜单、按钮、页面元素的可见与可用（enable/disable），无权限元素不展示或置灰。

* **FR-37（高）** 后端应对每个 API 调用做服务端权限校验，不得仅依赖前端隐藏；未授权调用返回拒绝并记录日志。

* **FR-38（高）** 前后端权限判定应使用同一权限数据源，避免口径不一致。

* **FR-39（中）** 系统应提供前端权限查询接口，返回当前用户在某系统的菜单 / 按钮 / 元素权限集合。

### 4.9 权限变更即时生效与并发互斥



* **FR-40（高）** 后端权限变更后，前端应即时响应：无需重新登录、无需手动刷新即生效；采用权限缓存立即失效与 / 或推送更新机制。

* **FR-41（高）** 系统应对并发 / 冲突操作加互斥控制（如同时授予互斥角色、同时修改同一授权关系），保证数据一致性。

* **FR-42（高）** 权限变更应记录变更前后快照，支持追溯。

* **FR-43（中）** 系统应支持变更通知：向受影响的业务系统推送权限失效 / 更新事件。

### 4.10 操作审计日志



* **FR-44（高）** 系统应记录操作审计日志，字段至少包含：操作时间、操作内容 / 动作、用户名、操作成功与否；建议扩展操作对象、来源 IP、所属系统。

* **FR-45（高）** 日志应**永久保存，不得定期删除**；支持按时间、用户名、操作类型、成功与否查询。

* **FR-46（高）** 日志应支持导出（如 CSV/Excel），导出操作本身亦记录日志。

* **FR-47（中）** 日志应防篡改（只追加、不可修改），并支持归档存储与容量规划。

### 4.11 敏感信息加密与脱敏



* **FR-48（高）** 员工姓名、电话号码等敏感个人信息应加密存储（如国密 / AES 加密），密钥独立管理。

* **FR-49（高）** 敏感信息展示时应脱敏（姓名保留姓氏、电话中间四位掩码），仅授权场景可申请查看明文并记录日志。

* **FR-50（中）** 敏感信息导出应默认脱敏，导出明文需审批并记录日志。

## 5. 关键业务流程

### 5.1 授权流程



1. 需求提出：部门经理 / 项目经理根据岗位职责提出权限申请（系统、功能点、数据范围）。

2. 审批：按审批链审批（部门经理→系统管理员；涉及敏感权限加签）。

3. 校验：系统校验角色互斥、最小权限、数据范围合法性。

4. 执行：系统管理员人工授予角色 — 功能点 / 数据范围，绑定用户 — 角色。

5. 生效：权限缓存失效 / 推送，前端即时生效；记录变更快照与审计日志。

6. 通知：通知申请人及受影响业务系统。

### 5.2 员工调岗权限变更流程



1. 触发：人力资源管理系统产生调岗事件（或系统管理员手工发起）。

2. 复核：系统列出该员工现有角色与数据权限，标记与新岗位不符项。

3. 调整：回收原岗位角色与数据范围，授予新岗位角色与数据范围（人工手动执行）。

4. 校验：互斥校验、最小权限校验。

5. 生效与留痕：即时生效，记录变更前后快照与审计日志。

### 5.3 员工离职封存流程



1. 触发：人力资源管理系统产生离职事件。

2. 封存：账号状态置为 "封存"，禁用登录。

3. 解绑：解除全部业务角色与数据权限绑定。

4. 保留：账号与历史日志保留，不做物理删除；日志可查。

5. 校验：确认该账号无法登录任何业务系统（令牌吊销）。

6. 留痕：记录封存操作日志。

### 5.4 权限变更后前端即时生效流程



1. 系统管理员提交权限变更并保存。

2. 后端更新权限数据，生成变更事件。

3. 权限缓存立即失效（或向在线会话推送更新）。

4. 前端下次请求权限查询接口时获得最新权限集合，菜单 / 按钮 / 元素即时刷新。

5. 无需重新登录、无需手动刷新；变更记录审计日志。

### 5.5 一次 API 访问的鉴权决策流程



1. 用户在前端发起业务请求，携带令牌。

2. 业务系统调用本系统鉴权接口校验令牌（有效性、有效期、是否吊销）。

3. 本系统返回用户身份及在该系统的功能权限与数据权限。

4. 业务系统后端校验：功能点操作权限是否满足；数据是否在授权范围内（分公司 / 部门 / 项目 / 本人）。

5. 校验通过则执行业务并返回；不通过则拒绝（返回无权限），记录审计日志（含成功与否）。

6. 全程不得仅依赖前端隐藏。

## 6. 非功能性需求

### 6.1 安全



* **NFR-01（高）** 敏感信息加密存储、展示脱敏；密钥独立管理，禁止硬编码。

* **NFR-02（高）** 遵循最小权限原则，默认无权限，授权方可访问。

* **NFR-03（高）** 防越权：后端每个 API 均校验，防止水平越权（同角色跨数据）与垂直越权（低权限访问高权限功能）。

* **NFR-04（高）** 令牌应签名防伪造，支持吊销；登录与鉴权接口应防重放。

* **NFR-05（中）** 管理后台操作应支持二次确认与操作留痕。

### 6.2 性能



* **NFR-06（高）** 支持 10000 人规模账号与 18 套系统、约 359 个功能点的权限管理。

* **NFR-07（高）** 单次接口鉴权延迟应满足业务系统调用要求（目标：平均 ≤ 100ms，峰值 ≤ 200ms，具体以设计阶段压测为准）。

* **NFR-08（中）** 权限查询接口应支持缓存，缓存失效策略与即时生效要求协调。

### 6.3 日志永久存储与归档



* **NFR-09（高）** 审计日志永久保存，不得定期删除；采用只追加存储。

* **NFR-10（中）** 日志按容量规划归档，归档后仍可查询导出；归档不改变 "永久保存" 属性。

### 6.4 可用性



* **NFR-11（高）** 本系统作为公司级 IAM，应具备高可用设计（避免单点），鉴权服务不可用时业务系统应有降级策略（如短时缓存鉴权结果，需评审）。

* **NFR-12（中）** 管理界面应易用，权限矩阵可视化，操作有明确反馈。

### 6.5 可扩展性



* **NFR-13（高）** 新增第 19 套系统接入应只需：登记系统与功能点、映射 API、配置角色权限，无需改动本系统核心代码。

* **NFR-14（中）** 功能点操作取值集合应可扩展，兼容现有 12 种取值。

* **NFR-15（中）** 组织树、角色模型应支持后续扩展（如增加分公司、增加岗位型数据角色）。

## 7. 对外接口需求

本系统向 18 套业务系统提供以下鉴权接口形态（具体协议在设计阶段细化）：



1. **令牌校验接口**：输入令牌，输出有效性、用户标识、过期时间；令牌无效 / 吊销返回失败。

2. **权限查询接口**：输入用户标识与系统编码，返回该用户在该系统的功能权限集合（功能点→操作）与数据权限范围（全公司 / 本分公司 / 本部门 / 本项目 / 本人及具体组织 / 项目标识）。

3. **SSO 认证接口**：支持业务系统跳转认证，认证成功回跳并携带令牌。

4. **权限变更通知接口**：权限变更时向业务系统推送失效 / 更新事件（可选，业务系统亦可主动查询）。

5. **接入登记接口**：业务系统登记系统编码、回调地址、密钥，用于第 19 套系统扩展接入。

接口调用均应记录审计日志（调用方、时间、结果）。
