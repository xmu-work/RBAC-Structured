'''

=== 1. 总体说明

本系统是公司级 IAM（身份与访问管理）平台，不重写 18 套业务系统，而是集中管控约 1 万名员工在这些系统中的"身份、功能权限、数据权限、登录态与操作留痕"。

ER 图共 _14 个实体_，按业务域分为四组：

. 身份与组织域：组织机构、账号/员工
. RBAC 授权核心：角色、角色互斥、用户-角色绑定、角色-功能授权、角色-数据范围授权、数据范围字典
. 业务软件接入域：业务接入系统、功能模块、功能点
. 运行凭证与审计域：令牌、审计日志、权限变更记录

整体模型即课程要求的 _RBAC0（用户—角色—权限三层）_，并在此基础上扩展了数据权限、敏感信息加密、离职封存、日志永久保存等硬性需求。

'''

=== 2. 各实体与项目板块对照

==== 2.1 身份与组织域

[cols="1,1"]
|===
| 实体（表名） | 对应项目中的板块

| **组织机构**（iam_org） | 公司四级组织树：总公司 → 9 个分公司（道路/桥梁/隧道/轨道/管网/水务/园林/照明/养护）→ 各分公司职能部 → 第一~第四项目经理部。`parent_id` 自关联表示父子层级；它同时是数据权限"本分公司/本部门/本项目"的判定依据。

| **账号/员工**（iam_user） | 全公司约 1 万名员工的统一账号。`name_enc / phone_enc` 实现**姓名、电话号码加密存储**；`account_status`（NORMAL/SEALED 等）对应在职状态与**离职封存（禁用但保留账号与日志）**。
|===

==== 2.2 RBAC 授权核心

[cols="1,1"]
|===
| 实体（表名） | 对应项目中的板块

| **角色**（iam_role） | 五类功能角色（系统管理员、公司领导、部门经理、项目经理、普通员工）+ 岗位型数据角色（安全员、预算员、质检员、造价员、会计、出纳等）。`parent_id` 表示角色继承。

| **角色互斥**（iam_role_exclusion） | 对应"操作系统互斥"的落地：例如会计与出纳不能同时授给同一人，授予时校验并拒绝冲突。

| **用户-角色绑定**（iam_user_role） | 记录"谁拥有哪个角色"的关联表；`expire_time` 支持临时授权到期自动回收。

| **角色-功能授权**（iam_role_function） | 对应"前端 enable/disable + 后端 API 鉴权"：把功能点连同操作（查看/新增/编辑/审批/导出等）授给角色，`allowed_action` 即现有 12 种操作取值。

| **角色-数据范围授权**（iam_role_data_scope） | 对应"数据权限"：安全员只能看本分公司安全数据、预算员只能看本项目预算，`scope_type + org_id/project_id` 圈定可见数据范围。

| **数据范围字典**（iam_data_scope） | 数据范围枚举：全公司 / 本分公司 / 本部门 / 本项目 / 本人。
|===

==== 2.3 业务软件接入域

[cols="1,1"]
|===
| 实体（表名） | 对应项目中的板块

| **业务接入系统**（iam_system） | 登记 18 套在跑系统（OA、PMIS、财务、安全生产、合同、成本等），含 system_code、回调地址、接入密钥；新增第 19 套系统时在此登记即可，无需改核心代码。

| **功能模块**（iam_module） | 每套系统下的功能模块（如 OA 下的公文管理、流程审批、会议管理）。

| **功能点**（iam_function_point） | 约 359 个最小可授权单元；`api_path + method` 是后端按 API 做服务端鉴权的依据（不能只靠前端隐藏按钮）。
|===

==== 2.4 运行凭证与审计域

[cols="1,1"]
|===
| 实体（表名） | 对应项目中的板块

| **令牌**（iam_token） | SSO 单点登录凭证，员工一次登录后访问各业务系统靠它；`revoked` 对应权限变更/离职后吊销令牌，实现"后端一改、前端即时失效"。

| **审计日志**（iam_audit_log） | 对应"日志永久保存"：记录操作时间、操作内容、用户名、成功与否；只追加、不修改、不删除，可查询导出。

| **权限变更记录**（iam_permission_change_log） | 每次授权、调岗、离职封存的变更前后快照，用于追溯"谁在何时被改了什么权限"。
|===

'''

=== 3. 一句话串联

* _组织机构 / 账号_：解决"人在哪个组织、账号是谁、是否在职封存"。
* _角色 / 互斥 / 用户-角色_：解决"把什么角色授给谁、互斥角色不许同授"。
* _角色-功能授权_：解决"能进哪个系统、点哪个按钮、调哪个 API"。
* _角色-数据范围授权_：解决"能看哪个分公司/部门/项目的数据"。
* _业务接入系统 / 模块 / 功能点_：被统一管控的那 18 套软件及其功能清单。
* _令牌_：解决登录态与单点登录、权限变更即时失效。
* _审计日志 / 权限变更记录_：解决操作永久留痕、变更可追溯。

'''

=== 4. 与硬性需求的对应关系

[cols="1,1"]
|===
| 甲方要求 | 在 ER 图中的落点

| 日志永久保存 | 审计日志（只追加）+ 权限变更记录

| 姓名、电话加密 | 账号表 `name_enc / phone_enc`

| 前端 enable/disable、后端 API 鉴权 | 角色-功能授权（功能点+API 映射+操作）

| 操作互斥 | 角色互斥表 + 授权校验

| 后端改权限、前端即时响应 | 令牌吊销 + 变更记录触发缓存失效

| 人员变动手动授权、离职封存保留账号删权限 | 账号状态 + 用户-角色绑定解绑（不物理删除）

| 功能权限 + 数据权限 | 角色-功能授权 与 角色-数据范围授权 双轨

| 安全员/预算员/质检员差异 | 岗位型数据角色 + 数据范围授权
|===

'''
